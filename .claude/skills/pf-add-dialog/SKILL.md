**Never hand-create the prefab and never copy an existing dialog/widget folder** (rule #13).

## 3. What lands

| Kind | Prefab (a **variant** of the framework template) | Controller | View |
|---|---|---|---|
| Dialog | `Content/UI/Reward/Prefabs/RewardDialog.prefab` | `Features/RewardDialog/RewardDialog.cs` | `Views/RewardDialog/RewardDialogView.cs` |
| Widget | `…/RewardWidget.prefab` | `Features/RewardWidget/RewardWidget.cs` | `Views/…/RewardView.cs` |
| Toast | `…/RewardToast.prefab` | *(none)* | `Views/…/RewardView.cs` |

Dialog template required node: **`SafeArea`, and only that**. The prefab is a **Prefab Variant**, so
template improvements flow into every SKU dialog.

**Never author a `Backdrop` node in a dialog prefab.** Both things behind a dialog are service-owned:
the **input gate** is `PF/Blocker` — invisible (alpha `0`, `raycastTarget: 1`), **one per modal
dialog**, because it must sit directly beneath the dialog it protects — and the **dim** is
`PF/DialogDim`, raised **once per modal *stack*** (on the empty → non-empty crossing) and destroyed
when the stack empties. Blocking input is a property of a dialog; dimming is a property of the stack.
A prefab-authored backdrop is the **second** dimming surface and composites with the service's: a 0.65
node over the 0.60 dim reads 0.86 instead of 0.60, and unlike the service's dim it is per *dialog*, so
it deepens as dialogs stack. **No gate catches it** — `requiredNodes` is a presence contract (missing
node, or a variant stripping one); there is no forbidden-node check, so this is a review rule. Dim
opacity lives in **one** place — the `PF/DialogDim` prefab. `DialogOptions(Modeless: true)` opts out of
both.

## 4. The dialog controller — and the `Aborted` reason

`RewardDialog : DialogBase<TResult>` — a plain class, never a MonoBehaviour.

`ShowAsync` returns a **reason**, not a bare value, because a dead scope is an expected outcome, not
an exception:

```csharp
var result = await _dialogs.ShowAsync<RewardDialog, RewardResult>(args, ct);
if (result.Reason == DialogCloseReason.Aborted) return;   // handle it — never fall through
```

Falling through on `Aborted` is how a reward gets granted twice.

## 5. Widgets: decide the composition mode BEFORE step 1

**First check it really is a widget — ask the anchoring question, per object (rule #16).** Anchored
to a screen edge or the safe area (HUD, score, top bar, currency pill) ⇒ yes, and it goes under the
`GetHost` of the layer that owns it: `Ui` for screen furniture, `Popup` for what the dialog stack
owns, `Overlay` for system overlays. Anchored to a position in the game's own space ⇒ it is not a
widget; ask how it draws instead (`Renderer` ⇒ `WorldRoot` + `Stamp`, see `pf-world-space`). Decide
this **per object**, never once for a feature: a score readout above a `Renderer`-drawn board is a
widget even though everything around it is world content — and there **mode A is unavailable** (a
uGUI widget cannot nest inside a world-space prefab, which has no `Canvas` ancestor), so the
manifest path below is forced.

A widget controller is a **plain `IDisposable`** with a `CreateAsync`/`Attach` leg, screen-owned
(`Lifetime.Scoped` in the screen's `SceneLifetimeScope`). There is **no `IWidgetService` and no
`WidgetBase`** (FR-074) — do not add one.

The mode decides whether there is a manifest entry at all:

| Mode | The View is… | Manifest entry | Editor shows the layout |
|---|---|---|---|
| **A — authored** ⭐ default | a nested prefab instance inside the parent's prefab | **none** — it is just a View | ✅ |
| **B — composed** | loaded via `IAssetService` and `Instantiate`d at runtime | `game.widgets.json` | ❌ empty slot |

**Pick B only when** presence is conditional (flag / A-B / tier gate), the asset must load or bundle
separately, the widget is Root-owned and outlives the screen, or the count comes from data — and
that last case is a **pool**, not N controllers.

Choosing B for an always-present widget is the standard way an unreviewable layout ships.

Three things B costs that A does not: its own `Stamp` call (a parent's recursive `Stamp` cannot
cover a GameObject instantiated later), one `Release` per `LoadAsync` on every path including the
failed-create unwind (rule #11), and — when mounted under `GetHost(RenderLayers.Ui)` rather than a
parent slot — explicit `SetVisible` plumbing through `OnEnter`/`OnPause`/`OnResume`/`OnExit`,
because a sibling of the screen's View is not hidden by the screen's `SetActive(false)`.

**Wiring direction, both modes:** the **controller finds the View** (`GetComponent`, or a
`[SerializeField]` the parent View exposes). A View never resolves or references its controller.

**Nesting stays flat.** A sub-widget is ctor-injected by its parent widget and registered beside it
in the same scope — the screen never learns it exists, and nothing is threaded through intermediate
constructors. Never register a widget `Lifetime.Transient`: VContainer disposes `IDisposable` only
for `Scoped`/`Singleton`.

## 6. Animation — C# only, no prefab edit

```csharp
public override ViewTransition CreateTransition()          // on your …DialogView : DialogViewBase
    => ViewTransition.Combine(new FadeTransition(0.2f), new ScaleTransition(0.92f));
```

Shipped: `FadeTransition` (adds a `CanvasGroup` at runtime if the prefab lacks one) and `ScaleTransition`.
For a house feel on **every** dialog, register an `IDialogTransitionFactory` at **Root** scope in the SKU
installer instead — a dialog that declares nothing inherits it. Its own override wins; return
`ViewTransition.None` to opt one dialog out of the default. Return a **fresh instance per call** — a
transition binds to one view and holds one live handle.

The framework owns the snap, the shown end state (applied non-virtually, so skipping `base` still ends
visible), the interactability window, a cap that cancels a hung leg, and cancelling an in-flight leg before
starting the other (`Stop()` is called for you). A custom transition ensures what it needs in `Bind` —
never require it on the prefab.
Full rules: **`docs/framework/recipes/add-dialog.md` §5**.

## 7. Layout is human zone

The prefab's uGUI hierarchy, `TextProxy` TMP stacks, anchors, and nested prefab instances go through
**Unity-MCP against a live editor** (rule #12). Never edit the `.prefab` YAML — it corrupts GUIDs
and fileIDs.

## 8. Gate

`Framework/Scaffold/Check` (mode-B widgets and all dialogs), plus both View tests at review.

## If it breaks

| Symptom | Cause |
|---|---|
| The result is always default | The `Aborted` reason is being ignored at the call site. |
| A widget's layout was never reviewable | Mode B was chosen for an always-present widget — move it to mode A. |
| A widget stays on screen over the next screen | Mode B under the render-layer host is a sibling, not a child; plumb `SetVisible`. |
| A widget is parented but invisible | `Stamp` was skipped on its own subtree. |
| Review rejects the View | It branches on game state, or it references its controller. |
| The screen darkens further with each stacked dialog | Something dims per dialog — find and delete the `Backdrop` node. One dim per stack, service-owned. No gate reports it. |
| The dim is the wrong darkness | Edit the `PF/DialogDim` prefab's Image alpha. There is no other knob. |
| The prefab lost its template link | It was hand-created, not scaffolded. Delete and re-run `Scaffold.Sync`. |
| A `.prefab` diff is huge and full of fileID churn | Someone edited YAML directly. Revert; redo via Unity-MCP. |
| The dialog works but looks like a greybox | Rule #17 — load `pf-visual-design` and walk the finished-surface checklist. Layout being human zone constrains the *mechanism*, not who picks the look. |
