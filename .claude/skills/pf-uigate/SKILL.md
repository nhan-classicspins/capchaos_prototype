# UiGate — the floor, then the ceiling

Both tools ship with the framework and are **synced**, not authored per SKU: they land at
`Tools/pf/` and carry a `GENERATED by PrototypeFramework <version>` header. Editing one there is
pointless — the next `agentdocs` sync reverts it and `--check` is red until then. Change it in the
framework repo (`Documentation~/agent/tools/`). See `docs/framework/sync-contract.md`.

What stays in the SKU is the **data**: `Tools/UiGate/probes/`, `contracts/`, `references/`,
`captures/`, `judge-calibration.md`, `tuning/` (calibration suites, baselines, run history).
Coordinates and token names belong to one game; the tools do not.

## The capture harness — where `captures/*.png` and `probes/*.layout.json` come from

Both gates read a capture. The framework also ships the thing that **takes** it:
`ClassicSpins.PrototypeFramework.Editor.Capture` (menu **Framework/UiGate/Run All Capture Fixtures**).
EditMode only — a preview scene, one manual render, no play session, no batchmode.

| The framework owns | The SKU owns |
|---|---|
| `CaptureRig` (preview scene, ruler-correct camera + world-space canvas, uGUI settle, URP-safe render, PNG) | one `ICaptureProject`: fixture folder, `TokenSource` (its `DesignTokens.cs`), `Load` (parse) and `Plan` (validate against the game's rules) |
| `CaptureHarness` (fixture → PNG → layout → `--generate` → probe, `0/1/2`, negative fixtures) | one surface per drawable screen: `CaptureSurface<TContext>` with `Id`, `Build` (END state, no time) and `Publish` (probes + masked regions after the settle) |
| `CaptureSurfaceRegistry` / `CaptureProjects` (discovered through `TypeCache` — nothing to register) | its `*.fixture.json` documents and, if its surfaces need game state, a `CaptureContext` subclass returned from `ICapturePlan.CreateContext` |
| `ProbeLayoutEmitter`, `PixelProbeRunner`, `RegionSeparation`, `AlphaMaskedLuminance`, `LabelFitProbe` | the field assertions (EditMode tests) that read `CaptureRigResult.Pixels` / `Regions` |

- **Entry points.** `CaptureHarness.RunAll(out report)` (the menu) or `CaptureHarness.Run(
  CaptureHarness.FixturePath("<stem>"))` for one fixture — the call an EditMode test or an MCP
  `script-execute` makes. Each fixture declares its `outcome` (`captured` · `flat-capture` ·
  `refused`), and `RunAll` is green when every fixture met its own declaration.
- **Outputs, fixed paths.** `Tools/UiGate/captures/<stem>.png` (regenerated, git-ignored),
  `Tools/UiGate/probes/<stem>.layout.json` + `<stem>.json` (committed). A surface that publishes no
  probe is settled by the flat-capture check alone.
- **Extents are names.** A fixture says `"extent": "base"` (1080x1920) or `"tall"` (1080x2400); width in
  world units is fixed at 1080, a taller extent only adds vertical bleed.
- **The ground is the SKU's token** (`ICapturePlan.Ground`), never a rig default — an empty-region
  probe must read the colour the game draws.
- **Anything a surface creates in code** (`new Texture2D`, `Sprite.Create`) goes into
  `context.Temporaries`; the rig destroys it in its `finally`.
- The SKU's Editor assembly (and its EditMode test assembly) reference
  `ClassicSpins.PrototypeFramework.Editor` for this.

## The two gates

| | Floor | Ceiling |
|---|---|---|
| Command | `Tools/pf/pixel-probe.py` | `Tools/pf/visual-judge.sh` |
| Question | *Is this wired up at all?* | *Does it look right?* |
| Answers with | arithmetic — CIE76 ΔE against a design token | a vision model, against an approved reference |
| Costs | nothing, and answers the same way every time | a model call and quota |
| Story kind | `kind: function` → `## Render Floor` | `kind: finish` → `## Visual Contract` |

**Run the floor first, always.** It is free, it is reproducible, and a floor failure makes every
ceiling verdict meaningless — a frame that did not render comes back with every contract row VIOLATED
and every one of those verdicts names the wrong cause.

```sh
Tools/pf/pixel-probe.py --capture Tools/UiGate/captures/<surface>.png \
                        --points  Tools/UiGate/probes/<surface>.json

Tools/pf/visual-judge.sh --spec <spec.md>        # inputs come from the contract's own block
```

**The judge's inputs live in the contract, not on the command line.** A `## Visual Contract` ends with
one fenced ` ```visual-judge ` block naming every image and note the rows need:

```visual-judge
root: <design package>                              # base for reference: and notes: paths
reference: mockups/<surface>-01.png | approved mockup — rows 1-8
reference: imports/<benchmark>.png | finish benchmark — row 9 only
capture: Tools/UiGate/captures/<fixture>.png | fixture <fixture> — rows 1-9
notes: DIVERGENCES.md#<surface>
```

Every caller — the implementing stage, the audit, the review lens, a measurement — runs the same
`--spec <spec.md>` and so judges the same images. A row that compares against an image the judge was
never handed returns CANNOT-TELL forever, or worse, SATISFIED on anything; the block is where that is
prevented once instead of remembered at every call site. `--capture`, `--reference` (both repeatable,
`path|label`) and `--notes file#section` still work and are added to the block. The prompt carries a
numbered legend of every image, so each V-line cites which capture and which reference it read.

**Pin the model.** The judge runs Codex with `--ignore-user-config`, which also drops the user's own
model and effort. Put `VISUAL_JUDGE_MODEL=` and `VISUAL_JUDGE_EFFORT=` in the SKU's
`Tools/UiGate/judge.conf`; a catch rate measured on one model says nothing about another.

**Let the judge own its clock.** It sends each image downscaled to a 768 px short side and encoded
as JPEG q90 4:4:4 (`UIGATE_JUDGE_FORMAT`; any image with transparency stays PNG). That is 2.1 MB for
nine images, against 8.3 MB as PNG. Measured on the same inputs, interleaved in the same time
windows: 63–76 s per call as JPEG, 398–860 s as PNG, with the same token count. Every model call runs
under one ceiling for the whole run, `UIGATE_JUDGE_TIMEOUT` (default 840 s). When it fires, the
judge exits `2` saying "no answer within Ns". So:

- **Never wrap the judge in a shorter `pf-timeout`.** A run killed early can never answer, and the
  next attempt then looks like a dead transport. Story 8.1 lost 104 minutes and an escalation to
  seven such attempts, capped at 280–900 s, each on a call that needed up to 14 minutes as PNG.
- **Give the host enough room:** Claude Code's `Bash` defaults to a 2-minute cap. Pass
  `timeout: 900000` on the call that runs the judge.
- `ERROR: Reconnecting… n/5` is the transport retrying, not a failure. It answers or it hits the
  ceiling.

**Let it vote.** The model is not deterministic. Measured 2026-09-23: an input judged all-SATISFIED
that morning came back with three rows VIOLATED in 3 of 3 re-runs that evening, on byte-identical
bytes. A single call, and the cache hit that replays it, can therefore sign off a borderline row by
luck. So the judge votes by default: `UIGATE_JUDGE_SAMPLES=K` (default **2**; set it in `judge.conf`) makes K calls in parallel, and adds one call at a time
for any row they split, up to 2K-1 in all. A row counts only when K calls agree. A row that never
reaches K comes back `VIOLATED — unsettled`, with its votes on the line. `K=2` costs about 75 s of
wall time as JPEG and 2–3× the judge tokens. Raising K changes what the calibration measured, so
re-run it.

`--dry-run` on the judge does every check, prints the prompt and the exact `codex` argv, and stops
before spending a model call. Use it whenever you are verifying wiring rather than pixels.
`--caller <name>` tags the archive record (stage, audit, lens…) so a run's judge calls can be
counted per call site; `--measure` samples the same input repeatedly without the cache or the HALT
check, for measuring the judge rather than the UI.

## Exit codes — two of them are not about the UI

`CliConventions.ExitCode`, as everywhere else: `0` Ok · `1` Drift · `2` Error. The judge adds `3`.

| Code | `pixel-probe.py` | `visual-judge.sh` |
|---|---|---|
| `0` | every probe inside tolerance | every row SATISFIED or CANNOT-TELL |
| `1` | at least one probe outside tolerance | at least one row VIOLATED |
| `2` | could not run — **including BROKEN CAPTURE** | could not run — no `codex`, no contract, **BROKEN CAPTURE** |
| `3` | — | **HALT**: the loop is not converging |

**`2` is a broken capture, not a wrong UI.** The flat-capture check runs *first* and outranks every
probe: a frame that is very nearly one flat colour did not render, and reporting that as `1` would
name a UI defect that does not exist. This is not hypothetical — `Tools/UiGate/judge-calibration.md`
records the Game View's render texture reading back a uniform `RGBA(0.098, 0.098, 0.122, 1)` across
the whole frame, and the loop that met it spent model calls to be told, wrongly, that the UI was
broken. **Fix the capture, then re-run.** Never "fix" the UI in response to a `2`.

**`3` is HALT: the row is asking the fixture for something it cannot give.** The judge reads its own
archive back before calling the model. Same row VIOLATED in each of the last two runs *and* this
capture byte-identical to the last one ⇒ the model has nothing new to look at and will answer exactly
as it did twice already. **Stop coding and re-read the row.** A row that needs a state the fixture
never enters, or an asset the fixture does not load, is a contract defect — reword the row or change
the fixture. Iterating the View is how this spins four rounds for nothing.

Every judge run archives to `Tools/UiGate/captures/<surface>/<stamp>-<verdict>.{png,md}`: the capture
as judged, the model, the reference, the V-lines, and the hash of the contract that produced them.
That archive is what the HALT check reads; it is also the only record of where a drift started.

## Producing the probe data for a new SKU — five steps

The points file is **machine-generated**. Nothing in it is hand-typed, which is the whole reason the
numbers in it can be trusted.

1. **`bmad-ux` names the elements.** For each surface it produces the list of things on it and the
   design token each one is expected to be drawn from. That is the *what* — it exists before any code.
2. **The story that builds the surface knows the real rect.** It writes the field assertions, so it
   already holds the anchors, the sizes and the parenting. That is the *where*.
3. **Write `Tools/UiGate/probes/<surface>.layout.json`** (schema `pixel-probe-layout/v1`) from (1) and
   (2): anchored rects × token names — no coordinates in pixels and no hex values, only names and
   anchors. With the capture harness this file is **emitted**, not typed: the surface's `Publish`
   adds a `CaptureProbePoint` per element (rect resolved from the sprite's alpha or read off the
   settled `RectTransform`, plus the token name), and the harness writes the layout and runs step 4.
4. **Generate the points file:**
   `Tools/pf/pixel-probe.py --generate Tools/UiGate/probes/<surface>.layout.json --out Tools/UiGate/probes/<surface>.json`
5. **A token change means regenerate, never hand-edit.** The generated file says so in its own
   `generated` field. A hand-edited points file is a gate that certifies whatever it was edited to
   say — the failure mode this whole pipeline is built to avoid.

## Why the rect is an address, not the thing under test

The obvious objection is that a probe checks a coordinate the same story chose, and is therefore
circular. It is not, because **the rect and the colour are proven by different rungs.**

- **The rect is proven by a field assertion.** `anchoredPosition`, `sizeDelta`, the parent, the
  anchors — all of them are numbers the engine-free or EditMode suite reads back directly, exactly,
  and for free. The probe never re-checks any of them.
- **The probe asks one question at that address: is the colour that reached the screen the colour the
  token says?** That is a question no field assertion can answer, because it is not a field — it is
  the output of the whole render path.

So a probe catches precisely the class of failure that is green in every field and wrong on screen:

- the wrong material or shader bound to a correctly placed renderer,
- a colour-space mistake — a linear value written where an sRGB one was meant, or the reverse (ΔE76
  is computed in CIELAB and is most sensitive to L\*, which is exactly what a colour-space slip
  moves),
- MSAA or post-processing altering what a correct colour becomes,
- a renderer that is disabled, or on a camera's culling mask it should not be,
- a `sortingOrder` that reads correctly in the field and still ends up behind something on screen.

If a rect is wrong, the field assertion goes red — and the probe reads the wrong pixel and almost
certainly goes red too, saying so in a different voice. Neither gate is standing in for the other.

**One tolerance, one meaning.** ΔE76 rather than an RGB distance because sRGB distance is not
perceptually even: 20 units apart is glaring in a dark navy and invisible in a cream, so one repo-wide
RGB tolerance is either too tight on the lights or too loose on the darks. ~1 is the just-noticeable
difference, ~2–3 is "a careful eye sees it", >10 is "those are different colours".

## What belongs where

| The claim | Settle it with |
|---|---|
| "the tile sits at x=140, 96 wide" | a field assertion |
| "the ground is the deliberate token, not the rig default" | `pixel-probe.py` |
| "the badge label stays inside its fill" | `visual-judge.sh` |
| "the scale is 0.72, not 0.80" | a field assertion — the judge returns CANNOT-TELL, correctly |
| "the surface reads as finished, not as a wireframe" | `visual-judge.sh` + `pf-visual-design`'s checklist |

A `CANNOT-TELL` row is not a failure and not a pass: it is the signal to **write the field assertion
that settles it**, and to say in the spec which assertion that is. That is how the parameter checks
get derived rather than invented.

## Before either gate blocks anything

The judge's catch rate is a number, not a belief. Run the surface's mutation fixtures past it and
require it to catch each one while passing the clean capture; record the rate **with the model
identity that produced it**, and re-measure when the model or the prompt changes. Until that number
exists, a `VIOLATED` row is a **finding for triage**, not a unilateral block. An exit `2` is never a
pass — a judge that did not run has proven nothing.

The measuring tools ship beside the judge and read the same archive:

| Command | Does |
|---|---|
| `python3 Tools/pf/judge-calibrate.py [--suite Tools/UiGate/tuning/calibration/<surface>.json]` | runs a suite's clean and mutated cases through the judge; writes `judge-calibration.md` (catch rate, false-positive rate, consistency, model) and appends `tuning/calibration-history.jsonl` |
| `python3 Tools/pf/visual-scorecard.py --spec <spec.md> --variant <name>` | scores one finish-story run (fidelity, judge agreement, cost) into `tuning/runs/`. `--compare <story>` lists every scored run |
| `sh Tools/pf/promote-reference.sh <surface> <capture.png>…` | files a capture as `references/<surface>/` **only** if an `ok` judge record lists those exact bytes; the verdict travels in `PROVENANCE.md` |

Bounding the loop: **follow the judge's `LOOP:` line** (`continue` / `stop (…)` / `done`) instead of
counting rounds — the policy is the SKU's (`UIGATE_LOOP_POLICY=fixed|progress`,
`UIGATE_LOOP_MAX_ROUNDS`, default fixed 3), and `progress` stops at the first round that clears
nothing. Only judge a capture that changed; one round, one fix pass. The judge enforces the capture
rule itself: an input already judged (same prompt, same image bytes, same model, encoding and sample
count) returns its archived verdict as a cache hit, with no model call and no new round. Exit `3`
stops the loop whose edits never reach the pixels. A cache hit **replays** a verdict; it does not
re-derive one. That is why the number of agreeing samples is part of the key: what gets frozen
should be a settled verdict, not one draw.

A row that stays near 50/50 across samples is not a coding problem. Story 8.1's V13 (the source-row
warning) sat on that boundary: VIOLATED in 6/6 calls on one capture, and 1 in 3 on the shipped one.
The warning and the destination were two warm hues, ΔE 32 apart, where the reference specimen used a
red. Iterating the View does not settle a row like that. A person deciding the treatment does: route
it to the design owner, and write down which way it was decided.

Capturing the frame at all — the play-mode budget, `screenshot-game-view`, `runInBackground`, the FHD
sizing trap — belongs to `pf-gates` and `pf-visual-design`. This skill starts once a PNG exists.
