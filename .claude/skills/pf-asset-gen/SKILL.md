# asset-gen — art the design package does not supply

The design package (`_bmad-output/planning-artifacts/ux-designs/…`) is where a surface's art comes
from. **Look there first.** An asset that exists there is used as-is. Never generate a second version
of approved art. Some art the package does not have, and this skill is for those two cases:

| The art | Make it with |
|---|---|
| UI chrome drawn from tokens: panels, pills, buttons, glows, dashes, shadows | an Editor generator in code (`Editor/UI/*ArtGenerator.cs`). Deterministic, token-bound, no quota. `pf-visual-design` |
| Illustrated or painterly content the package lacks: an emblem, a prop, a scene | `asset-gen.py run`, `mode: generate`, with the package's approved art as `references` |
| A change to an approved plate: paint an object out, clean a background | `asset-gen.py run`, `mode: edit`, with `preserve` regions |

Faking the last two in code does not work. A cubby "painted out" with blurred rows is a streaked
smear. It survives only where something happens to cover it, and a reviewer who opens the PNG sees
it at once.

## The tool and the data

The tool is `Tools/pf/asset-gen.py` (synced from the framework, like `visual-judge.sh`). The data is
the SKU's own and lives under `Tools/AssetGen/` (`ASSETGEN_ROOT`), exactly as `Tools/UiGate/` sits
beside the judge:

| Path | What | Committed |
|---|---|---|
| `Tools/AssetGen/requests/<id>.json` | the request: reviewable, like a probe layout | yes |
| wherever the request's `out` points (conventionally `Tools/AssetGen/assets/`) | the selected PNG plus `<png>.gen.json` | yes |
| `Tools/AssetGen/candidates/<id>/` | every variant and its facts | no. The tool writes its own `.gitignore` |

Keep selected PNGs **outside `Assets/`**. They are inputs to an Editor generator, which writes the
imported sprite, not sprites themselves.

## The flow

```sh
python3 Tools/pf/asset-gen.py run    Tools/AssetGen/requests/<id>.json --variants 2
python3 Tools/pf/asset-gen.py select Tools/AssetGen/requests/<id>.json <n>
```

**Run it unsandboxed.** It needs the network, like the judge. Each variant takes about 50-80 s, and
variants run in parallel.

Exit codes: `0` ok · `1` a variant broke a `preserve` region · `2` error, or no image at all.

A request (`schema: asset-gen-request/v1`) carries these fields. Paths are repo-relative.

| Field | Meaning |
|---|---|
| `id` | one path segment |
| `mode` | `generate` or `edit` |
| `target` | edit only: the image being edited |
| `references` | `[{path, role}]`, attached after the target |
| `prompt` | name the images by attachment number |
| `out` | where `select` writes the chosen PNG |
| `preserve` | edit only: `[[x, y, w, h]…]` regions that must come back unchanged, checked as mean \|diff\| against the target (`preserve_tolerance`, default 8 of 255) |
| `consumer` | the file that reads `out` |

**Choose among variants by looking, not by the first one that exits 0.**
- Put the variants beside the approved art at display size, on the colour they will sit on.
- For an edit, prefer the variant with the lowest `preserve` drift that adds nothing competing with
  gameplay.
- A vision check (the judge, or one `codex exec` over a small JPEG contact sheet) catches a gross
  style mismatch. It flips on subtle ones, so take its verdict only when two runs agree.

## What a generation is not

- **Not deterministic.** The same prompt gives different art every run. The selected PNG is committed
  **source**, and nothing regenerates it in CI or in a test. The consuming Editor generator stays
  deterministic because it reads the committed file. Its "run twice, byte-identical" check still
  holds.
- **Not size-controlled.**
  - A generate call returns 1254×1254 whatever size the prompt asks for.
  - Framing asked for in the prompt (a box, a baseline) is not honoured.
  - An edit keeps the target's size, and regions outside the change move about 2-4 of 255.
  - Crop, baseline, PPU 1 and nine-slice belong to the consuming generator. Never rely on the model
    for them.
- **Not a finished decision.** `select` writes `status: pending-user-review` into the `.gen.json`.
  The asset ships like a pending-user-review mockup: it does not block the story, and a person flips
  the status when they approve it.

## Budget and stopping

At most about 6 generations per story. If two rounds of variants miss, stop and escalate: the
request is the problem, not luck. A plate edit that keeps drifting `preserve` needs a narrower
prompt or a narrower preserve region, not a third round.

The capture gates still decide. After the consuming generator runs, `pixel-probe.py` and
`visual-judge.sh` judge the render as for any other art (`pf-uigate`).

## Why the wrapper, not a bare `codex exec`

- **Given write access, the model post-processes its own output without saying so.** It was seen
  resizing with `sips`. The tool therefore runs `-s read-only` and copies the original from
  `$CODEX_HOME/generated_images/<thread_id>/` itself.
- **`--json` names the thread but emits no image event.** The directory listing is the only reliable
  locator.
- **The call runs from a temporary directory outside the repo.** The repo's `AGENTS.md` and hooks
  are meant for coding agents, not for this call.
- **It calls `~/.local/bin/codex` directly.** A terminal shim on PATH would otherwise inject hooks.
  Override with `CODEX_BIN`.
