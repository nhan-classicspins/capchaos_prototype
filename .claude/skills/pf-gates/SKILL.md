# Commands, gates, and co-dev

Full detail: **`docs/framework/AGENTS.framework.md`** §5–§8.

## Exit-code contract — every surface

**`0` Ok · `1` Drift** (check-mode staleness) **· `2` Error** (bad args / parse / toolchain fault).

## Editor doors

## Command line (needs a dev-linked framework checkout)

```sh
Tools/Build/pf-build.sh agentdocs --check   # agent-doc pack drift
Tools/Build/pf-build.sh codegen  --check    # typed-key drift
Tools/Build/pf-build.sh validate            # loc CSV: dup keys/locales + cross-locale format-args
sh Tools/CI/greps.sh source                 # input-poll in Views · lifecycle hooks · MessagePipe reg
sh Tools/CI/greps.sh poolleak <logfile>     # [PoolLeak] in a run log is an ERROR, not noise
```

All of the above are engine-free `dotnet`/`sh` — safe to run with the Editor open. The `test`,
`content` and `player` surfaces shell out to Unity in `-batchmode` and are **CI-only**; an agent never
runs them locally (see Test cadence below).

The manifests live **outside `Assets/`**, so editing one raises no Unity import event — codegen must
be run explicitly. That is the single most common cause of "the generated key will not compile".

## Test cadence — engine-free in the loop, Unity only where it can run

Canonical text: `AGENTS.framework.md` §8a. Three rungs, **only the first has no Unity in it**, and
**only the first two belong in a loop at all** — plus two observed play sessions that are neither a
rung nor a suite.

| Rung | How you run it locally | Cost | When |
|---|---|---|---|
| Engine-free (plain .NET) | the SKU's gate script — `sh Tools/pf/gate.sh` — never a bare `dotnet test <project>` | seconds | **Every iteration** |
| Unity EditMode | `Tools/pf/pf-tests` (one synchronous run through MCP `script-execute`) | seconds for the fast tier | **Editor-side** code changed |
| Unity PlayMode **suite** | **you don't** — CI owns it | n/a locally | never local |

**Rung 1 has a door, and the bare command is not it.** A SKU's engine-free suite carries tests that
are deliberately outside the per-edit loop — a sweep, a soak, a fuzz — tagged with a category its gate
script filters out (`DEFAULT_TEST_FILTER="TestCategory!=Slow"` in this layout). `dotnet test <project>`
with no `--filter` runs **all** of them. Measured on a SKU here: the unfiltered command pulled in a
10 000-level generator sweep that is CI's, sat at 98 % CPU for over twenty minutes across four
invocations in one story, was killed by vstest's blame collector as a hung test host, and cost roughly
35 minutes of wall clock and a quarter of that story's spend — while the suite it was meant to prove
takes 90 seconds behind the filter. So:

- **Run `sh Tools/pf/gate.sh`** (greps + headless type-check + the filtered suite, one invocation,
  exit `0`/`1`/`2`). The script is synced; what is the SKU's own lives beside it, never in it.
  `Tools/Gate/gate.conf.sh` sets `TEST_PROJECT`, plus an optional `KEYED_TEST`: one Slow test re-run
  by name only when its inputs' hash changes. `Tools/Gate/greps.local.sh` adds the SKU's own
  `grep_*` functions to the shared framework-rule greps. With no `gate.conf.sh` the gate exits `2`
  and names the one line to write.
- **Never invent the command.** If you are about to type `dotnet test` with a project path and no
  `--filter`, you are about to run the sweeps. Read the gate script first; its settings are in `Tools/Gate/gate.conf.sh`.
- **Cap anything you are not sure terminates.** **macOS ships no `timeout(1)`** — `timeout 480 …` is
  `command not found`, and the usual recovery is to re-run it uncapped, which is the real cost. Use
  the synced `Tools/pf/pf-timeout SECONDS COMMAND …`: exit `124` on the cap, and it signals the
  child's whole **process group**, so a `dotnet test` that forks a `testhost` leaves no orphan
  burning a core and no "another test run is in progress" on the next attempt.

**And the slow set stops itself — the filter is not the only line of defence.** A filter is a
property of the *command*, so it only protects the commands someone remembered to write down; an
IDE's Run All, a fresh CI step and an agent typing from memory all walk straight past it. Put the
guard in the *test* instead, where it holds for every caller. One attribute that is both the
category and the opt-in, so neither can be applied without the other:

```csharp
// SkuHeadlessTests/SlowTestAttribute.cs — the Setup Wizard's `testkit` emit writes it (with TestCategories.cs,
// Gate/SlowOptInTests.cs, Gate/AssemblyReferenceTests.cs, Tools/Gate/gate.conf.sh) into a SKU that has none.
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method)]
public sealed class SlowAttribute : CategoryAttribute, IApplyToTest
{
    public SlowAttribute() : base(TestCategories.Slow) { }

    // NUnit 4's CategoryAttribute.ApplyToTest is NOT virtual — re-implementing the interface on the
    // derived type is the seam, and it wins interface dispatch.
    void IApplyToTest.ApplyToTest(Test test)
    {
        test.Properties.Add(PropertyNames.Category, Name);
        if (SlowGate.OptedIn) return;                       // PF_RUN_SLOW=1
        test.RunState = RunState.Ignored;                   // NOT Explicit: an exact-name filter
        test.Properties.Set(PropertyNames.SkipReason, SlowGate.SkipReason);   // still selects Explicit
    }
}
```

Then `[Slow]` replaces every `[Category(TestCategories.Slow)]`, and a reflection test asserts nothing
reaches the category by another route. **The skip is never silent**: the run prints
`Skipped <name>` with a reason that names `PF_RUN_SLOW`, so "the sweep did not run" lands on the
summary line instead of being assumed — which is what AD-14 asks of any leg you did not execute.

Measured on this project, on the exact command that used to hang: `dotnet test <project>` with no
filter now returns in **1m40s — 914 passed, 3 skipped** (the two sweeps and the fuzz), against a
20+ minute CPU burn and a killed test host before. Keep the gate's filter as well: it is cheaper
still, and `SlowCategoryFilterTests` keeps the filter and the category spelled the same.

Below the first rung sits the **type-check gate** — it runs no test, it answers *does this still
compile*, and it is the cheapest way to close a loop after an edit. Two synced tools, same
`GENERATED` header and same `Tools/pf/` as the rest:

```sh
Tools/pf/typecheck-headless.sh                  # engine-free assemblies, no UnityEngine reference
Tools/pf/typecheck.sh Game.Views                # one assembly, Unity references resolved
Tools/pf/typecheck.sh --changed                 # only the asmdefs touched since HEAD
```

Quiet on success (`OK <asm> (Ns)`), deduped `error CS####` lines and a non-zero exit on failure;
cache in `Library/pf-typecheck/`. `typecheck-headless.sh` doubles as the engine-freedom check — an
assembly that has grown a Unity dependency fails here rather than in review. Cross-assembly
references resolve from `Library/ScriptAssemblies/<Asm>.dll`, so a stale prebuilt DLL can hide a
fresh signature break: refresh Unity once at the end of a stage to confirm. Escalate to
`assets-refresh` **only** when the type-check is green but a source generator, ILPP, or
`AssetDatabase` change needs a domain reload.

Beside the three sit **two things that are neither a rung nor a suite** — both one observed play-mode
session via MCP `editor-application-set-state`, both running no tests:

| Session | Earned by | Answers | Output |
|---|---|---|---|
| **Boot smoke** | bootstrap/**wiring** — boot node, DI registration, asmdef, scaffold manifest, RenderLayer, event route, scene rig, first-scene config | *does this still start?* | a clean log |
| **Visual check** | a change that **draws** — View, prefab, scene content, design token, layout, transition, any UI/UX surface | *does this look right on screen?* | **screenshots you read** |

**Play mode is for looking, never for iterating** — see "Never sweep in play mode" below. The ceiling is
shared and counts **entries into play mode**: one session can serve as both.

### Every MCP result lands in your context — filter before you read

An MCP tool result is appended to your conversation verbatim and then re-sent on **every** later turn,
so a fat result is not paid once, it is paid for the rest of the session. On a real project
`console-get-logs` is the worst offender: single entries carry whole codegen transcripts and stack
traces, and one unfiltered call with `count: 8` has measured **~4 MB**. A wide `assets-get-data` and
`tests-run` with `includePassingTests: true` have the same shape.

Every Unity tool is also reachable from Bash, where the shell reduces the payload before it ever
enters context:

```sh
npx --yes unity-mcp-cli run-tool console-get-logs --input '{"count":20}' 2>&1 | python3 -c "
import sys, json
raw = sys.stdin.read(); d = json.loads(raw[raw.find('{'):])
for e in d['structured']['result']:
    print(e.get('LogType'), '::', e.get('Message','').replace(chr(10), ' | ')[:250])
"
```

- `run-tool <name>` for tools, `run-system-tool ping` for the transport probe; `--input-file -` with a
  heredoc when the payload is multi-line C#.
- The CLI is usually **not on `PATH`** — invoke it as `npx --yes unity-mcp-cli`.
- Always cap `count` and filter by `LogType`. Read the errors, not the transcript.
- `tests-run`: leave `includePassingTests` false — the failure list is the evidence; a pass list is noise.

**Keep the direct `mcp__…` tools** for calls whose result is already small and structured —
`editor-application-get-state`, `scene-list-opened`, a targeted `assets-find`, `assets-refresh`.
**Route through the CLI** anything that returns logs, test output, or an asset dump.

Measured on one story, one implementation subagent: 23 direct `console-get-logs` calls put **162k
tokens** into a context that was then re-read more than a hundred times; the same story driven through
the filtered CLI put **zero**.

#### Two synced tools do the batching and the reducing for you

`Tools/pf/pf-exec` and `Tools/pf/pf-mcp` are framework-synced like the UI gates (same `GENERATED`
header, same `Tools/pf/`). They are **turn savers, not gates** — they prove nothing on their own; they
make N inspections cost **one** turn instead of N, each result capped before it enters context.

```sh
Tools/pf/pf-exec --cap 2k <<'EOF'   # INDEPENDENT reads/greps, in parallel, one labelled report
sig    : rg -n "class BoardView" Assets
tokens : read Assets/<sku>/Design/DesignTokens.cs:1-40
EOF

Tools/pf/pf-mcp <<'EOF'              # ORDERED Unity-MCP calls, reduced, stops on the first failure
assets-refresh   {}
console-get-logs {"count":20,"logType":"Error"}
tests-run        {"testMode":"EditMode","testAssembly":"Game.Tests.Editor"}
EOF
```

**`pf-mcp --timeout` is seconds, defaults to 300, and is forwarded to the CLI** — whose own default is
**60**. That single number has been read as a Unity failure more than once: `tests-run` comes back
`Tool call timed out after 60 seconds` while the Editor runs the suite to completion behind it, and the
caller then guesses at a `sleep`. It is a client-side abort, nothing else. Two consequences worth
holding: pass `--timeout` when a call can legitimately run long, and when a tool answers `Processing`
(a domain reload deferred the run), **poll the artefact it writes by mtime — never a fixed sleep**. A
blind `sleep 300` after an 88-second suite is five minutes bought for ninety seconds of work, and it
costs a turn at full context on each side of the wait.

**`pf-mcp` stops starting new items after `--turn-budget` seconds** (default 240). The rest go to a
file, and the run ends `INCOMPLETE … continue: Tools/pf/pf-mcp < FILE` with exit 1. Continue with
exactly that command in the next call. A subagent's prompt cache lives five minutes, and one Bash
call that blocks longer than that makes the next turn re-write the whole context. Measured on
story 8.1: a 729 s batch of 43 per-class `tests-run` items cost about $2.50 in cache writes alone.
Never "work around" the budget by pushing the whole assembly into ONE `tests-run` either: past about
300 s the MCP gateway answers HTTP 504 while the suite keeps running. **Tests do not go through
`pf-mcp` at all any more — they go through `Tools/pf/pf-tests`** (next section but one).

`pf-mcp` runs items **one at a time** (the Editor is single-threaded and later items depend on earlier
ones), applies the reducers above by tool name — logs → `LogType :: message[:250]`, tests → failures
plus the count line, `screenshot-*` → the **path**, never the pixels — and warns once a run crosses the
ten-entries-into-play-mode ceiling. **`Tools/pf/pf-write` — N file mutations in one turn, all-or-nothing.** Batched *writing* needs
no tool: the host runs every `Write`/`Edit` call a single assistant message carries before it
calls you again, so six files created together cost one turn — measured here, the same six-file
task costs **47k context tokens batched against 330k one-at-a-time**. What a message cannot give
you is atomicity, and that is what this door is for: a set of mutations that must all land or
none of them.

```sh
Tools/pf/pf-write <<'EOF'
[ {"op":"edit","path":"src/A.cs","old":"var x = 1;","new":"var x = 2;"},
  {"op":"edit","path":"src/B.cs","old":"foo(","new":"bar(","count":3},
  {"op":"write","path":"src/C.cs","text":"// whole file\n"},
  {"op":"delete","path":"src/Old.cs"} ]
EOF
```

JSON, so no delimiter can collide with the code you are writing. **Every item is validated
before anything is touched, and any failure mid-apply rolls the whole tree back** — the opposite
of `pf-exec`, where a failing item is allowed to stand. `edit` requires exactly `count`
occurrences (default 1): an ambiguous match is refused, never guessed. `--dry-run` validates
without writing. Not for test runs or commits — a result you must judge stays its own turn.

`pf-exec` is for items that depend on nothing; anything ordered
belongs in `pf-mcp` when it drives the Editor, and in `pf-exec --ordered --stop-on-fail`
when it is shell — build, then test, then gate. Add `--reduce auto` there: it keeps each
leg's PASS/FAIL, the test counts, the failing names and the compiler errors, and drops the
restore chatter and VSTest banner behind them. A red compile then never pays for the test
run and the gate behind it.

```sh
Tools/pf/pf-exec --ordered --stop-on-fail --reduce auto <<'EOF'
build : dotnet build -nologo
gate  : sh Tools/pf/gate.sh
EOF
```
 `--help` on either for the flags.

### Never run Unity batchmode locally

**No agent runs `pf-build.sh test`, `content`, or `player` locally.** Not "prefer not to", not "unless
the Editor is closed" — never. Two reasons, either sufficient:

1. **It cannot run while the Editor is open** — which during dev is always. The open project holds
   `Temp/UnityLockfile`; a second Unity in `-batchmode` aborts on it before any test executes.
   (Closed-Editor batchmode does work — that is CI's situation, not a dev loop's.)
2. **It lies when it fails.** The gate ignores Unity's exit code and reads the NUnit XML. An aborted
   run writes none, so the gate reads the **previous** run's XML and prints a green `result=Passed`
   for a run that never happened.

All three surfaces now refuse this themselves: exit `2` naming `Temp/UnityLockfile`, and `test`
additionally moves any prior results XML aside to `<results>.prev` before launching. Seeing that exit 2
means *use MCP, or leave it to CI* — never *close the human's Editor*. Unity leaves that file behind
when killed or hung on exit, so an orphan can outlive every Editor: `PF_ALLOW_LOCKED=1` overrides,
correct **only** after confirming no Editor runs.

**The PlayMode suite is never run locally by any door** — not batchmode, not MCP `tests-run` with
`testMode: "PlayMode"`. The two observed sessions are a different thing and are allowed when earned; see
below. The split to hold in your head: entering play mode to **look** at a UI change is a **duty**;
running the PlayMode **suite** is still CI's.

**And no worktree / second clone:** it dodges the lock but pays a full `Library` import, costing more
than the run it enables.

**Batchmode belongs exclusively to CI.** A dev loop that never launches Unity is safe **because** of
CI's Unity step — so that step is a claim to check, not a fact to lean on. The ban holds regardless;
what changes is what you may *report*. In this repo step 4 is declared unconditional yet
`docs/m5-pilot-acceptance.md` marks it **DEFERRED**, no PlayMode artifact has ever existed, and
batchmode PlayMode is recorded as stalling (`Owner: framework/playmode-batchmode-stall`). Declaration is
not execution: report **CI-owned, unverified**.

### The rules

**Earns EditMode (via MCP):** a menu item, importer, Doctor check, scaffold or codegen tool — i.e.
**Editor-side** code.

**Earns the boot smoke:** **bootstrap/wiring** — a boot node · a DI registration · an asmdef · a
scaffold manifest · a RenderLayer · an event route · a scene rig · the first-scene config. Once, when
the change is complete. Procedure below.

**Earns the visual check:** a change that **draws** — View · prefab · scene content · design token ·
layout · transition/animation · any UI/UX surface a player looks at; also "engine-free green but it
still looks wrong on screen". One play session, the states you named captured with
`screenshot-game-view`, the images **read and attached**. Procedure below. Rule #17's *finished is the
default* is not claimable about a screen nobody looked at.

**Still never run locally: the PlayMode _suite_** (`tests-run`, `testMode: "PlayMode"`). The visual
check replaces the eyeball, not the suite — a View's automated PlayMode fixtures stay CI's. Say which
half is unproven; never block waiting for a human to run the suite for you.

**Earns nothing:** model/rules/parsing edits the engine-free suite proves · doc or comment edits · a
refactor that suite covers end to end · "just to be safe". **Fits none of these?** Run MCP EditMode and
report the change PlayMode-unproven — never batchmode, never an unearned play session. **No engine-free
project here?** Then MCP EditMode is the inner loop.

**Both lists fire? Take one session for both.** A turn that changes wiring *and* a View earns boot smoke
and visual check — that is **one** entry into play mode, read twice, reported on two lines.

### The two play sessions — one boot / one look, never a suite

Every rung above is blind twice over. It is blind to **wiring**: the engine-free suite never builds the
container, EditMode never enters play mode, and a bad boot node fails as *nothing starts* rather than as
a wrong number. And it is blind to **appearance**: nothing above can draw a frame, so a View that
compiles, passes every assertion and renders as a grey rectangle is green all the way down. So two
narrow doors stay open, against the **already-open** Editor — same mechanism, same preconditions, same
ceiling.

**Preconditions — skipping any one turns the smoke into a false green.** `editor-application-get-state`
first: already in play mode ⇒ someone is using the Editor, abort (`isPlaying: true` would be a no-op you
read as a boot). Every open scene **saved** and the **right** scene open — play mode runs what is in
memory, and a wrong-scene boot builds no container yet logs nothing. Compilation **finished**, not
merely not-failed: refresh and let it settle, or you boot stale assemblies.

```
console-clear-logs                                # takes the human's console too — say so
editor-application-set-state  { "isPlaying": true }
  … wait for a completion signal you can name …
  … VISUAL CHECK: reach each named state (script-execute / gameobject-* if it needs input) …
screenshot-game-view                              # once per named state — these images ARE the output
  … screenshot-camera for one camera · screenshot-isolated for one object on a clean ground …
console-get-logs                                  # explicit maxEntries; the default cap truncates
editor-application-set-state  { "isPlaying": false }
console-get-logs                                  # AGAIN — [PoolLeak] is emitted on scope DISPOSE
```

**Capture at FHD in the project's own orientation** — `1080×1920` portrait, `1920×1080` landscape; read
which off the rig's design rect (`WorldSpaceCanvasScaler.ReferenceResolution` / the host's
`CanvasCameraFitter._referenceResolution`), never hardcode the other one. `screenshot-camera` defaults to
landscape FHD **and swaps that aspect onto the camera**, so on a portrait rig an unsized capture shows an
aspect the game never ships — and corrupts every later capture in the same session.

**The visual check's own two obligations.** *(1) State the budget before you enter* — the states you
will capture, **by name**, and a wall-clock ceiling with what you do on hitting it (exit, report what
you got, name what you missed). A session you cannot describe in advance is a **sweep**. *(2) Read the
images, do not just attach them* — against `pf-visual-design`'s finished-surface checklist and the
artist spec if one exists: deliberate ground, drawn empty states, one spacing rhythm, a type hierarchy,
nothing clipped at the safe rect, nothing overlapping, legible at device size. Then write what you saw.
A capture with no written reading is a file, not evidence; a visual check with no images is not a
visual check.

**Two gates settle a capture once you have one.** `Tools/pf/pixel-probe.py` is the deterministic
floor — *did anything render, is it the right colour* — no model, no quota, run it first. Then
`Tools/pf/visual-judge.sh` is the vision-model ceiling — *does it look right against the approved
reference*. Both are framework-synced tools; both add exit codes that are **not** "the UI is wrong"
(`2` = broken capture, `3` = HALT). Procedure, probe authoring, and the full code table:
`pf-uigate`.

### Never sweep in play mode

**Play mode is for looking, never for iterating.** Both sessions are one sitting with a stated end.
Never drive from play mode locally:

- **a content-set sweep** — every level in the catalogue, every palette entry, every table row.
  **Hundreds of levels is the canonical forbidden case.**
- **solver / exhaustive / combinatorial runs** — "are all N levels solvable", every permutation of a rule.
- **soak, perf, or long timed simulation** — "leave it running and see"; anything measured in minutes.
- **anything with no bound you can state before you start it.** That is the definition of a sweep.

Not merely slow — play mode is a **false home** for these. They are data-and-rules questions, which the
**engine-free** rung answers in seconds, deterministically, naming the failing case; a play-mode sweep
answers with a frozen Editor, a human locked out, and no artefact. Needs the engine at that scale? **CI's.**

**Sample, never sweep.** Want visual confidence over a large set? Capture a **named handful** — first,
last, the extremes the spec calls out — and say in the report that it is a sample and which members it
covers. Three named levels with screenshots is evidence. "I played through them" is not.

**Never** MCP `tests-run` with `testMode: "PlayMode"`, never batchmode — those run the suite, and the
suite is CI's. Leave play mode exited.

**Two reads, deliberately.** Boot is async (awaited nodes, first-scene load, Addressables), so a read
fired straight after `isPlaying: true` can precede the failure; and rule #11's `[PoolLeak]` WARN only
appears on dispose, *after* play mode exits.

**Pass ≠ "no exceptions".** Warnings count — a `[PoolLeak]` WARN is a **bug**, not noise. And silence is
not a boot: a node awaiting forever logs nothing, so require a **positive** completion signal inside a
bound you state; no signal is a **red**.

**When:** at the point the change is **complete**, not between edits. **Ceiling: ten entries into play
mode in one dev turn** (it counts entries — not reasons for them). *One dev turn* = one unit of work
handed back to a human; **one session covers every change completed in it**, boot smoke and visual check
together, and the headroom above that is for re-entering after a fix. **An eleventh entry into play mode
in one dev turn** means you are looping: stop and drop a rung.

**What each proves — nothing else.** The boot smoke: the app booted and the log is clean. The visual
check: what was on screen in the states you captured, at this machine's aspect ratio — nothing about the
states you skipped, nothing about a device. Neither is a PlayMode test pass; both prove **never that a
suite passed**. Each gets **its own line**: *"boot smoke clean (MCP, 1 boot); visual check: 3 states
captured (board L1, level-complete dialog, empty state), screenshots attached and read against the
checklist; PlayMode suite not run — CI-owned, unverified."*

**Red?** Fix, re-boot to confirm — a confirm boot is well inside the ceiling. **Three reds on the same
cause ⇒ stop booting**: name it and hand it over rather than re-entering to re-read a failure you
already have. A red you have not
investigated never goes to CI as "unverified"; a red the change never touched is **pre-existing** — name
it, don't repair unrelated breakage.

**Both lists fire? The earn wins** — as with EditMode. Editor-side *and* wiring earns **both**: EditMode
first, then the session. **Unearned play mode is still banned** — not by MCP, not by pressing Play "just
to have a look" at a change that draws nothing.

**Door shut?** (Shuts both sessions — same door.) Compilation failing (fix it, don't retry blindly) ·
unfocused Editor on macOS, where MCP **stalls** rather than failing cleanly — don't sit waiting · no
Unity-MCP in this SKU at all. One answer for all three: **no batchmode fallback** — ask the human to
focus, else name the session you could not take and hand it to CI.

**The unfocused-Editor trap, specifically — check the setting first.** With *Run In Background* **off**,
Unity's player loop only advances while the window is focused and repainting, so an unattended play mode
sits at `Time.frameCount == 1`: every PlayerLoop-driven `await` in boot hangs to its node's hard timeout
and nothing is ever drawn to capture. The fix is one project setting — `runInBackground: 1` in
`ProjectSettings/ProjectSettings.asset` (*Player ▸ Resolution and Presentation ▸ Run In Background*,
`PlayerSettings.runInBackground`) — and the **Setup Wizard's compose writes it**, so only a SKU composed
before that step (or one that turned it off) still has it. It does **not** cure Unity-MCP's macOS focus
stall: if the MCP call itself hangs, the door is shut whatever the setting says. A genuinely shut door is
**not a red** — don't file the timeouts as product bugs, and never report a blank capture as a visual
check.

### An EditMode pass is never evidence about runtime

EditMode reaches only assemblies declaring `"includePlatforms": ["Editor"]`. In **this repo** that is
the framework's `Tests/Editor` alone, holding Editor *tooling* fixtures; `Tests/Runtime` and the sample
SKU's `Game.Tests` are both `"includePlatforms": []` and PlayMode-only — so framework runtime and SKU
Views have **zero** local coverage. Never report an EditMode pass as runtime coverage, and **never quote
a test count you did not just observe** (attribute counts under-report, and nothing pins them).

**Nor assume the rung is green.** This repo's last recorded batchmode EditMode run was red (two
`BuildEntryEditorTests`, owner `framework/build-entry-appid-test`), and those failures are
batchmode-specific — no `FrameworkSettings` resolved — so green under MCP and red in CI are both
expected from the same code. Say which door you used.

**Why MCP EditMode is cheaper — accurately.** *Not* because it skips a domain reload: `tests-run`
refreshes the AssetDatabase and resumes across a reload if scripts changed. It avoids the **Editor boot
and project import** (comparing EditMode to EditMode, neither side enters play mode). Its two preconditions both fail loudly: every open
scene must be **saved** (a dirty scene aborts with `InvalidOperationException`), and on macOS the
Unity window must be **focused** or MCP returns null — it is a **human-attended** door by
construction, which is why it is never the scripted or CI leg. **When MCP is unavailable** — null on an
unfocused/absent Editor (an unattended session is the usual way), or aborted on dirty scenes — do **not**
fall back to batchmode: ask the human to focus/save if one is there, else treat the rung like the
PlayMode suite (name it, hand it to CI, finish). An earned boot smoke dies the same way — no boot, not
a batchmode one.

**The EditMode door is `Tools/pf/pf-tests`, not a `tests-run` per class.** It sends one
`script-execute`, which starts ONE `TestRunnerApi` run over any set of classes with
`runSynchronously = true`. Unity writes the verdict to `Library/pf-tests/<id>.result.json`, and the
tool polls that file.

```sh
Tools/pf/pf-tests MapArtTests MapScreenTests   # inner loop: the classes you touched
Tools/pf/pf-tests --auto                        # stage receipt: fast tier, + Slow when the diff draws
Tools/pf/pf-tests --list                        # classes, counts, which are [Category("Slow")]
Tools/pf/pf-tests --wait <id>                   # after an INCOMPLETE (turn budget, not a failure)
```

Why it replaced the per-class `tests-run` sweep. Measured on a SKU, 2026-09-24, the Editor
unfocused:

- **An unfocused Editor ticks ~6 times a second** (96 `EditorApplication.update` calls in 15 s;
  9479 focused). Unity's async test runner advances one step per tick. That made every MCP
  `tests-run` cost ~8-10 s, even for an 8-test class whose own work is 0.015 s: 2.2 s focused,
  10-11 s unfocused. A synchronous run does not wait on ticks. The same 8 tests take ~0.7 s, and
  98 tests take 1.7 s instead of 13.4 s.
- **MCP `tests-run` takes one `testClass`**, so a suite became 45-60 calls. `Filter.groupNames` is
  an OR, so any set of classes is one run here.
- **No gateway cap.** No HTTP request stays open while tests run, so a whole-assembly run is legal.
  Measured: 674 tests in 297 s, one call plus one `--wait`.
- **Stamp reuse.** The same selection over byte-identical inputs is `reused`, which answers a
  parent re-verifying its stage agent's run.

**Keep the slow tier out of the loop.** Capture and floor fixtures render, and their
`OneTimeSetUp` draws a whole surface. Measured: 9 such classes took ~260 s of a 277 s suite; the
other 38 took ~18 s (~33 s wall through the tool). Mark them `[Category(EditorTestCategories.Slow)]`,
using a constant rather than a literal, for the same typo reason as rung 1's `TestCategories.Slow`.
`--all` then skips them and prints which it skipped. `--auto` adds them only when the working tree
(vs `HEAD`, untracked files included) touches a path that draws: `Views/`, `Content/`, `Capture/`,
`UiGate/`, `DesignTokens`, prefabs, images, materials, fonts. Override that with
`PF_TESTS_DRAW_PATHS`. A class you **name** always runs, Slow or not. No assembly split is needed:
selection happens in the filter, not by assembly name.

Rules that follow:

- **In the loop, name the classes.** `--auto` is the stage's receipt, run **once**.
- **A parent never re-runs its stage's receipt.** The stamp answers `reused` when nothing changed.
  After a review patch, run the patched classes by name, plus `--auto`, which re-runs only if the
  inputs moved.
- **One Unity call at a time.** A synchronous run holds the main thread, and every other MCP call
  queues behind it. pf-tests refuses to start while its own last run is live.
- A selection containing an `IEnumerator` test (`[UnityTest]`, `[UnitySetUp]`) falls back to the
  async runner and says so. It is correct, only slower.
- Exit `2` means it could not run: compile errors, an unsaved scene, an unknown class name. Fix the
  cause; never answer it with the old per-class sweep.

**Say what you skipped.** *"engine-free green; EditMode green (136); boot smoke clean (MCP, 1 boot);
visual check: 3 named states captured and read; PlayMode suite not run locally — CI owns it."* Never
phrase a partial run so a reader assumes the whole suite ran; report counts for what you did run, and
give the boot smoke and the visual check **each its own clause** — folding either into the suite's line
claims a suite you did not run. **And don't overstate CI:** you didn't watch it
run — report the Unity rungs as **CI-owned and unverified**.

**Ending a story:** engine-free → drift gates → MCP EditMode if earned → the one play session if
earned, last and once — boot smoke, visual check, or both. That is the whole local sequence; there is no final batchmode pass. If an earned run is
red, fix it and **re-run that rung once** before calling anything green. (A local working order, not CI's: CI runs drift at step 3,
Unity at 4, headless at 5.)

> **Precondition (AD-14: the tool is a convenience, CI is the guardrail).** Skipping the Unity rungs
> locally is safe *only* because CI re-runs them. **Check, don't assume** — grep the repo's workflows
> for `--platform PlayMode`. A leg that runs **and blocks the merge** ⇒ the default applies. A leg that
> is advisory, `if:`-narrowed, branch-filtered, skipped on forks, or declared in a repo with no remote
> **counts as no PlayMode leg**. No PlayMode leg, or no CI at all ⇒ nothing gates that suite: the local
> ban still stands, so **name the missing leg** and escalate to the human. An ungated suite is a human
> decision, not a hole for an agent to paper over. **The visual check narrows that hole, never closes
> it** — with no CI the screenshots are the only runtime evidence there is, so take them and read them
> properly, and still say plainly that the automated suite is ungated. Images of three screens are not
> a suite.

**An empty run is not a green run.** Because of the trap below, an EditMode rung can report **0
tests**. Zero executed is not evidence — say so rather than banking it.

**The `includePlatforms` trap.** A test asmdef with `"includePlatforms": []` is classified PlayMode
**in full** — the EditMode runner finds nothing in it, so even pure arithmetic is stranded behind a
rung nobody runs locally. Remedy: a sibling test assembly with `"includePlatforms": ["Editor"]` for
the engine-light fixtures. Where the SKU's spine pins its assembly set or asmdef fields, that sibling
is a **routed spine change**. Note the pack's own exemplars carry the trap.

**Trust the XML, not the exit code** — background for reading a CI log, not an invitation: batchmode
`-runTests` exit codes are unreliable, so `pf-build.sh test` gates on the parsed NUnit XML
(`--results`).

### Long Editor jobs — a timeout means *still running*

A gateway 504, a `pf-timeout` expiry or `Tool call timed out` means the client stopped waiting, not that
the Editor stopped working. The Editor is single-threaded: **never re-issue the call** — the second copy
queues behind the first and the Editor stays unresponsive twice as long. Measured on a SKU: a level
catalog menu item driven through MCP `script-execute` ran its seed search synchronously on the main
thread under Mono, outlived the 300 s gateway, was re-delivered, and left the Editor unresponsive for
hours — the story lost its whole verification stage.

So before driving any Editor job that can outlast one MCP call (a generator, a seed search, a bake, a
catalog build), **look for an engine-free door first**: a small `dotnet` tool under `Tools/<Name>/`
that compiles the SAME source file the menu item uses (link it with `<Compile Include>`, never copy it)
and writes the same bytes, with a `check` mode on the `0/1/2` contract. The menu item stays as the human
door; agents take the shell door. Where no such door exists yet, that is the first task, not a
`script-execute` with a longer timeout.

## A SKU never edits framework code

| Where you were about to edit | Why it is wrong |
|---|---|
| `Library/PackageCache/…` | Unity **overwrites it on every reimport/resolve** — your edit is silently lost. |
| An **embedded** `Packages/com.classicspins.prototype-framework` in a SKU repo | It **forks the shared package**: the fix never reaches other SKUs and drifts from upstream forever. |

The correct path: **dev-link** a framework checkout, fix it **in the framework repo**, run the
framework's own gate, bump the version your SKU pins.

### Dev-link modes (the framework entry in `Packages/manifest.json`)

| Mode | Entry | When |
|---|---|---|
| **pinned** ⭐ | `"com.classicspins.prototype-framework": "0.1.0"` or a git `…#v0.1.0` tag | CI / release — the clean default |
| **dev-link** | `"…": "file:../PrototypeFramework/Packages/com.classicspins.prototype-framework"` | Daily co-dev |
| **embedded** | *(no entry; physically under `Packages/`)* | A one-off local copy |

**Edit that entry by hand** — one line in `Packages/manifest.json`. No framework tool writes it and
none reports which mode you are in; pick the mode yourself from the table above.

## Triage: is this a local decision?

| Change | Route |
|---|---|
| **A logic bug** — wrong result, leak, off-by-one, **no boundary change** | Fix in the framework repo via dev-link, gate it, release. A normal local decision. |
| **A spine change** — new assembly, new reference edge, new RenderLayer, new kernel boot node, new event type, or editing a shipped migrator | **Route to architecture review.** Not a local decision. |

**If unsure, treat it as a spine change and route it.** An unnecessary review costs far less than an
unsanctioned spine edit shipped to every SKU.

## The framework runs its own gate BEFORE a version bump

In the **framework repo**:

```sh
cd HeadlessTests && dotnet test          # framework-pure ship gate
dotnet test SkuHeadlessTests             # sample-SKU gate — a SEPARATE CI step; the first says nothing about it
sh Tools/CI/greps.sh source
dotnet run --project Packages/com.classicspins.prototype-framework/Tools~/Codegen/ScaffoldCli -- --check
```

All four green **before** the `package.json` bump and tag. **Never bump-then-fix** — a red bump
ships the breakage to every SKU that pins the new version.

Adding a public framework type? Run `pf-build.sh agentdocs` and commit both regenerated
`framework-api.index.json` files first — `AgentDocsSyncTests` runs *inside* `dotnet test`, so a stale
pack reddens the ship gate with a failure that looks unrelated to your change.

## Cross-repo work tracking

`deferred-work.md` entries end with an `Owner:` tag in one of two buckets:
**`Owner: framework/*`** (fixed upstream, flows to every SKU) or **`Owner: SKU/*`** (local to one
game, never touches framework code).

## When `agentdocs --check` is red

The pinned framework version changed and the synced pack is stale, or someone hand-edited a
generated file. Run `Framework/Agent Docs/Sync` (or `pf-build.sh agentdocs`) and commit the result.
Never fix a generated doc by editing it in place — edit it in the framework repo under
`Documentation~/agent/` and re-sync.

The sync owns more than docs: `.claude/hooks/pf-subagent-context.py` + its `SubagentStart` entry in
`.claude/settings.json`, `_bmad/custom/*.pf.toml` (only where BMAD is installed), a marked block in
`.gitignore`, and three host keys — Bash `BASH_DEFAULT_TIMEOUT_MS`/`BASH_MAX_TIMEOUT_MS` (600000 /
900000), the Unity server's `timeout` in `.mcp.json` (900000) and the Unity-MCP plugin's `timeoutMs`
(600000). Those keys are minimums: a larger value is kept, a smaller one is drift. A drift line naming
`UserSettings/AI-Game-Developer-Config.json` right after a sync means the running plugin wrote its
in-memory value back — run the sync from the Editor menu, which raises the plugin's own setting first.
The full table is `docs/framework/sync-contract.md`.
