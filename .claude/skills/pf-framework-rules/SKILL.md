# PrototypeFramework — the enforced rules

## The five things that actually get a change rejected

1. **Framework code edited from inside the SKU.** Always wrong — see `pf-gates`.
2. **A command-style event** (`ShowDialogEvent`, `PlaySfxEvent`). Events are past-tense facts.
3. **A View that branches on game state.** See the two tests below.
4. **A script no assembly claims.** No ancestor `.asmdef`/`.asmref` ⇒ it compiles into
   `Assembly-CSharp`, green and outside the AD-1 boundary. Doctor check 15 names it.
5. **A spine change made without routing it.** New assembly *beyond the SKU's eight*, reference
   edge, RenderLayer, boot node, event type, or an edit to a shipped migrator.

## The two View review tests

A View answers *how it looks*. A controller answers *what happens*.

1. **The "why" test.** If a View method needs to know *why* it was called, that decision belongs in
   the controller. A View must not decide "if the player can't afford it, disable the button" — the
   controller decides and calls `SetBuyEnabled(false)`. **A View never branches on game state.**
2. **The gallery test.** Every View method must be callable in **any order**, in a scene preview,
   **without the game running** and **without any service**.

## Human zone vs machine zone

**Human zone** (drive Unity-MCP against a live editor; never edit `.unity`/`.prefab`/`.asset` YAML —
raw edits corrupt GUIDs/fileIDs): uGUI prefab layout including `TextProxy` TMP stacks, particle
tuning, lighting/GI bakes, audio mixer routing, Master-Scene rig work.

**Machine zone** (edit directly, diff-reviewable): `.cs`, `.asmdef`, `.json`, `.csv`, `.md`, `.sh`,
`.yml`.

> On macOS, Unity-MCP returns null while the Editor window is unfocused. A hanging or empty MCP call
> means "ask the user to focus the Editor" — never "fall back to editing YAML".
